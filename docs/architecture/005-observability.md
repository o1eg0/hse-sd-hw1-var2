# ADR-005: Observability (Draft)

> Статус: Draft \
> Команда: 9 \
> Дата: 2025-11-29

## Контекст

В текущей архитектуре проекта отсутствует централизованная система сбора мониторингов и логов. 

Это приводит к следующим проблемам:
- **Слепые зоны**: Мы не знаем текущую нагрузку (RPS), задержки (Latency), процент ошибок сервисов
- **Сложность отладки**: Для поиска причин ошибок необходимо подключаться к контейнерам и смотреть логи, что неэффективно при наличии нескольких инстансев. 
- **Отсутствие истории**: Логи теряются при перезапуске контейнера. Нет возможности проанализировать инциденты постфактум.

Необходимо решение для сбора, хранения и визуализации телеметрии.

## Решение

Внедрение PLG стека (Prometheus, Loki, Grafana) для обеспечения observability.

### Детали реализации

#### Метркии

Используем Prometheus для сбора и хранения метрик.

В Python-сервисах используем библиотеку `prometheus-fastapi-instrumentator`

Сервисы экспортируют метрики в формате Prometheus в эндпоинте `/metrics`.

Конфигурация скрейпинга задается декларативно в `prometheus.yml`

#### Логи

Используем Loki как систему аггрегации логов.

Для сбора логов используем агент Promtail. Он монтируется к `var/run/docker.sock` и собирает stdout/stderr всех контейнеров автоматически. 

#### Визуализация

Используем Grafana как единый интерфейс метрик и логов.

Конфигурация источников данных и дашбордов декларативно описывается в `yml`/`JSON` файлах. Это реализует подход "Monitoring as Code", позволяя хранить конфигурацию в Git.

## Альтернативы

* ELK стек (Elasticsearch, Logstash, Kibana):
    * **Плюсы**: Мощные возможности для полнотекстового поиска
    * **Минусы**: Ресурсоемкость (требуется больше RAM под Java heap). Сложность настройки и поддержки для небольшого проекта выше, чем у Loki.

* SaaS решения (Datadog):
    * **Плюсы**: Быстрый старт
    * **Минусы**: Высокая стоимость. Передача логов третьей стороне.

## Последствия

* Положительные:
    * Возможность видеть метрики и логи конкретного сервиса на одном экране в один момент времени.
    * Появилась техническая база для настройки алертинга.
    * Ясное понимание "узких мест" системы
* Риски:
    * Дополнительное потребление CPU/RAM ресурсов 
    * Требуется поддержка конфигураций при изменении кода
    * Необходимо следить за объемом диска для хранения логов и метрик
