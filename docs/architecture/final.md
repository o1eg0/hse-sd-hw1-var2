# ADR: Архитектура сервиса аренды пауэрбанков

> Статус: Draft \
> Команда: 9 \
> Дата: 2025-11-26

---

## 1. Контекст

Сервис аренды пауэрбанков

Требуется архитектура, выдерживающая:
- `X = 100 RPS` на создание заказа/старта аренды
- `Y = 50` просмотров информации об аренде на одну аренду
- `Z ~= 1` КБ на запись

Критичные внешние источники:
- `stations`, `payments`: при недоступности операция отменяется.

Некритичные:
- `tariffs`, `users`, `config`: должны иметь предсказуемую деградацию (кэш/фолбэки).

Обязательны:
- идемпотентность мутирующих операций
- контроль свежести оффера
- ручка текущей накопленной стоимости
- мультистраны и мультивалютность
- минимум 1 год хранения заказов и платежей, с политикой по стране

---

## 2. Функциональные требования

### 2.1 Оффер

- Создать оффер по станции и пользователю
- Проверять свежесть оффера
- Отклонять создание заказа по просроченному офферу

### 2.2 Заказ (аренда / rental)

Идемпотентный старт аренды по `Idempotency-Key`

При старте:
- зарезервировать/выдать пауэрбанк на станции (`stations`)
- зафиксировать выбранный тариф (snapshot тарифа)
- создать платёжную сессию в `payments` с учётом страны/валюты

Поддержать мультивалютность (валюта тарифа $\to$ валюта заказа)

### 2.3 Возврат

- Рассчитать итоговую стоимость аренды
- Списать оплату (capture/partial capture) через `payments`
- Вернуть пауэрбанк на станцию
- Завершить заказ (перевести в `RETURNED/CLOSED`)

### 2.4 Информация об аренде

`get_rent_info`:
- статус аренды
- страна, валюта
- текущая накопленная стоимость

### 2.5 Источники данных и деградация

Критичные:
- `stations`, `payments`: при недоступности операция не выполняется

Некритичные:
- `config`: минутный кэш, при недоступности используется кэшир. конфиг
- `tariffs`: LRU-кэш, при давности >10 минут $\to$ 5xx с меткой `tariffs_stale`
- `users`: фоллбэк на «жадный» тариф/лимиты, пометить в событии

## 3. Нефункциональные требования

### 3.1 Надёжность и согласованность

Идемпотентность:
- Все мутирующие запросы требуют заголовок `Idempotency-Key: <uuid>`
- Повтор с теми же параметрами $\to$ `200/201` и повтор того же тела ответа
- Повтор с другими параметрами $\to$ `409 Conflict`

Транзакционная запись заказа:
- запись в `offers`, `rentals`, `payments` в одной транзакции Postgres там, где это возможно
- outbox-таблица (или аналог) для интеграционных событий / компенсаций

Предсказуемая деградация некритичных источников (см. 2.5).

### 3.2 Хранение

Оценка размера записи: `Z ~= 1 КБ`

Хранение минимум 1 год:
- партиционирование таблиц заказов/платежей по месяцу и/или стране
- авто-чистка по политике удержания (retention) по стране

### 3.3 Наблюдаемость

Структурные логи (JSON), корреляция по `request_id`, `idempotency_key`

Метрики:
- RPS/latency по ручкам
- ошибки по внешним сервисам с тегами `stations_down`, `tariffs_stale`, и т.п.
- состояние кэшей (hit/miss)

### 3.4 Развёртывание
- Docker-контейнеры, локально: `docker-compose`
- Миграции БД: `alembic`

## 4. Архитектура сервисов и взаимодействия

### 4.1 Сервисы

`rental-api` - write-сервис / оркестратор:
- ручки: создание оффера, старт аренды, возврат
- реализация бизнес-логики и идемпотентности
- транзакции в PostgreSQL

`pricing`:
- расчёт текущей стоимости аренды и прайсинг-правила
- кэш тарифов и конфигурации в Redis (см. пункт 7) 

`rental-query` - read-сервис:
- отдаёт `get_rent_info` из Redis / materialized view / PG-реплики
- read-нагрузка изолирована от write 

Моки внешних сервисов:
- `stations`, `payments`, `tariffs`, `users`, `config` - отдельный контейнер

### 4.2 Взаимодействия (схема в словах)

1. Создание оффера, `rental-api`:
   - читает `tariffs` (через `pricing` и Redis)
   - читает `config` (через Redis-кэш)
   - создаёт запись `offers` в PostgreSQL

2. Старт аренды, `rental-api`:
   - проверяет `offers` (валидность и свежесть)
   - вызывает `stations` для резервирования/выдачи пауэрбанка
   - вызывает `payments` для `authorize`
   - пишет `rentals` и `payments` внутри транзакции
   - сохраняет идемпотентный ответ

3. Возврат аренды, `rental-api`:
   - обращается к `pricing` для финального расчёта стоимости
   - вызывает `payments`
   - обновляет `rentals`, `payments`

4. Запрос информации об аренде, `rental-query`:
   - обращается к PG-реплике
   - выдаёт DTO `get_rent_info`

## 5. Основные API-ручки

Ниже - обзор основных REST-ручек.

### 5.1 `rental-api`

`POST /offers`
  - Вход: `{ user_id, station_id }`
  - Выход: `Offer` (id, station, snapshot тарифа, expires_at, price_per_hour, deposit, …)

`POST /rentals/start`
  - Headers: `Idempotency-Key`
  - Вход: `{ offer_id, station_id, powerbank_id? }`
  - Действия: резерв станции, платёж authorize, создание `rental`.

`POST /rentals/{rental_id}/return`
  - Headers: `Idempotency-Key`
  - Вход: `{ station_id }`
  - Действия: финальный расчёт, capture/refund, возврат пауэрбанка, завершение аренды.

### 5.2 `rental-query`

`GET /rentals/{rental_id}`
  * Выход (формат NFR): 

    ```json
    {
      "order_id": "…",
      "status": "active",
      "user_id": "…",
      "country": "DE",
      "currency": "EUR",
      "started_at": "…",
      "ended_at": null,
      "accrued_amount": "100"
    }
    ```

### 5.3 `pricing` (внутренний API)

`GET /pricing/rentals/{rental_id}/accrued`
  - Возвращает текущую накопленную стоимость аренды.

`GET /pricing/tariffs/{tariff_id}`
  - Возвращает прайсинг-правила по тарифу (с кэшем в Redis).

## 6. Модель данных и таблицы

### 6.1 Доменные сущности → таблицы

На уровне домена сущности описаны так: User, Station, Powerbank, Tariff, Offer, Order, Payment, RetentionPolicy, Config. 

#### Таблица `offers`

Источник: класс `OfferDB`.

Основные поля:

* `id: str` — PK, индекс.
* `user_id: str` — FK на пользователя (логически), индекс.
* `station_id: str` — станция, индекс.
* `tariff_id: str` — ссылка на тариф.
* `country: str` (<=5) — код страны (например, `DE`).
* `currency: str` (<=5) — валюта (`EUR`, `USD`, …).
* `price_per_hour: int`
* `free_period_min: int`
* `deposit: int`
* `pricing_mode: enum(PricingMode)` — `NORMAL` / `FALLBACK_GREEDY`.
* `status: enum(OfferStatus)` — `ACTIVE/USED/EXPIRED/CANCELLED`.
* `expires_at: datetime`
* `created_at`, `updated_at: datetime`

Назначение: snapshot тарифа и условий на момент предложения.

#### Таблица `rentals` (заказы)

Источник: `RentalDB`.

Основные поля:

* `id: str` — PK, индекс.
* `offer_id: str` — FK → `offers.id`, индекс.
* `user_id: str` — индекс.
* `start_station_id: str`
* `finish_station_id: str | None`
* `country: str` (<=2), `currency: str` (<=3)
* `price_per_hour`, `free_period_min`, `deposit`
* `total_amount: int` — накопленная стоимость.
* `powerbank_id: str | None` — индекс.
* `start_time: datetime`, `finish_time: datetime | None`
* `status: enum(RentalStatus)` — `CREATED/ACTIVE/RETURNED/CLOSED`.
* `created_at`, `updated_at`.

Это физическая реализация доменной сущности **Order**. 

#### Таблица `payments`

Источник: `PaymentDB`.

Поля:

* `id: str` — PK.
* `order_id: str` — FK → `rentals.id`, индекс.
* `kind: enum(PaymentKind)` — `AUTHORIZE/CAPTURE/REFUND`.
* `amount: int`, `currency: str` (<=3).
* `status: enum(PaymentStatus)` — `PENDING/SUCCEEDED/FAILED`.
* `provider_ref: str | None`
* `created_at`, `updated_at`.

#### Таблица `country_retention_config`

Источник: `CountryRetentionConfigDB`.

Поля:

* `country: str` (<=2) — PK.
* `retention_days: int` — срок хранения заказов/платежей по стране.
* `created_at`, `updated_at`.

Используется для периодического удаления старых заказов и платежей по стране.

#### Таблица `idempotency_keys`

Источник: `IdempotencyKeyDB`.

Поля:

* `key: str` — PK, значение HTTP заголовка `Idempotency-Key`.
* `scope: enum(IdempotencyKeyScope)` — например, `RENTAL_START` (в перспективе: `OFFER_CREATE`, `RENTAL_RETURN`).
* `request_hash: str` — SHA-256 от нормализованного тела запроса.
* `response_body: str` — сериализованный JSON ответа.
* `created_at: datetime`.

Логика: при повторе с тем же ключом и хэшем отдаем сохранённый `response_body`; при конфликте параметров — `409`.

## 7. Кэширование внешних сервисов

### 7.1 Config service

Redis-кэш с TTL из `pricing_settings.config_ttl_sec`

Стратегия **cache-aside**:
  - при cache-miss идём в `config`;
  - при недоступности сервиса возвращаем fallback-конфиг:
    - `tariff_cache_ttl_sec = 600`
    - `offer_ttl_sec = 300`
    - `fallback_greedy_coeff = 2.0`
    - плюс дефолтные `price_coeff_settings`

Реализация: `httpx.AsyncClient` + `redis.asyncio`

### 7.2 Tariff service

Redis-кэш с TTL, задаваемым через `config` (или дефолт 600 секунд).

Стратегия **cache-aside** с быстрым фейлом:
  - при cache-miss и недоступности upstream $\to$ HTTP 503 `"Tariff data is stale or upstream unavailable"`.

Важно: дата добавления в кэш не проверяется (если ключ есть — считаем данные пригодными, пока TTL не истёк).

### 7.3 Альтернативы

**Circuit Breaker**: даёт автоматический переход в режим деградации, но увеличивает сложность разработки, поэтому отложен

**Без кэширования**: не удовлетворяет требованиям по отказоустойчивости и задержкам

## 8. Идемпотентность

### 8.1 Правила

Все `POST/PUT/DELETE` обязаны принимать заголовок `Idempotency-Key: <UUID v4>`

При отсутствии - `HTTP 400 Bad Request`

Храним: `key`, `scope`, `request_hash`, `response_body`, `created_at` в таблице `idempotency_keys`

TTL записи: 24 часа (чистим через `pg_cron`)

### 8.2 Последствия
Получаем **exactly-once** семантику для клиента при повторах

Защита от дублирования заказов и списаний

Оверхед: один дополнительный запрос к БД на каждую мутацию (+10-20ms)

## 9. Технологический стек

### 9.1 Язык и фреймворки

- Язык: **Python 3.11+**.
- Web-framework: **FastAPI** (асинхронный, нативный OpenAPI).
- ORM/модели: **SQLModel** (поверх SQLAlchemy, типизированные модели Python).
- Миграции: **Alembic**.

### 9.2 Хранилища и инфраструктура

Основная БД: **PostgreSQL** (партиционирование, индексы по id, user_id, station_id)

Кэш: **Redis** (tariffs, config, возможно, read-модель аренды)

Контейнеризация: **Docker**, локальное развёртывание: `docker-compose`

## 10. Оценка нагрузки и объёма данных

### 10.1 RPS

Пиковая нагрузка:
  - до **100 RPS** на создание/старт аренды
  - по условию до **50 просмотров информации по одной аренде** за её жизнь. При стабильном потоке заказов это даёт до ~5000 read-запросов на `get_rent_info` на тот же порядок, что и write

### 10.2 Объём БД

Из расчёта, что одна запись `~= 1 КБ` и `100 RPS` на старты аренды:

Заказы/год: `100 rps  60 x 60 x 24 x 365 ~= 3.15 x 10^9`

Объём только заказов: `3.15 x 10^9 x 1 КБ ~= 3.15 ТБ`

Офферы и платежи примерно 1:1 к заказам ещё `~ 6 ТБ`

Грубая верхняя оценка: **~ 9 ТБ/год** сырых данных

С учётом:
  - компрессии на уровне storage
  - агрессивной чистки офферов
  - retention по странам (меньше года для части стран): фактический объём будет ощутимо меньше, но верхний рубеж планирования `~10 ТБ/год`

## 11. Оценка объёма железа (ориентир)

### 11.1 Сервисы приложений

Предполагаем асинхронные Python-сервисы с FastAPI, 50–150ms среднее время ответа.

`rental-api`

RPS: до 100 write-запросов/сек (оффер, старт, возврат).

Подойдет:
  - 2 реплики по **2 vCPU, 2–4 ГБ RAM** каждая
  - Горизонтальное масштабирование при росте RPS

`pricing`

Нагрузка: CPU-лёгкие операции, большинство запросов обслуживаются из Redis.

Подойдет:
  - 2 реплики по **1–2 vCPU, 2 ГБ RAM**

`rental-query`

Основная read-нагрузка (`get_rent_info`), до нескольких тысяч RPS.

Подойдет:
  - 3 реплики по **2 vCPU, 2–4 ГБ RAM**
  - с опорой на Redis и PG-реплики

### 11.2 База данных PostgreSQL

Требуется:
  - выдерживать 100 RPS write + индексные операции;
  - хранить до ~10 ТБ данных за год (с запасом).

Гулять так гулять:
  - Primary:
    - **8 vCPU, 32 ГБ RAM**, быстрый NVMe.
    - Диск: минимум **10–12 ТБ** полезного объёма (с запасом >1 год + индексы).
  - 1–2 read-реплики:
    - по **4–8 vCPU, 16–32 ГБ RAM**,
    - по 4–8 ТБ диска каждая.

### 11.3 Redis

Хранится:
  - кэш тарифов,
  - кэш конфигурации,
  - возможно, кэш последних состояний аренды.

При разумных TTL объём относительно небольшой.

Подойдет:
  - Кластер из 1–3 нод:
    - **2–4 vCPU, 4–8 ГБ RAM**, SSD-диск на 50–100 ГБ.

## 12. Рассмотренные альтернативы и выбор

### 12.1 Монолит vs микросервисы

**Вариант 1: Монолит**

Плюсы:
- проще деплой и отладка
- одна кодовая база и БД

Минусы:
  - сложнее масштабировать read-нагрузку независимо от write
  - деградация одной части (например, тяжёлого `get_rent_info`) влияет на всё
  - труднее изолировать эксперименты с `pricing` и кэшированием

**Вариант 2: Логическое разделение на `rental-api`, `pricing`, `rental-query` (выбран)**

Плюсы:
  - разделение write (создание/изменение аренды) и read (`get_rent_info`);
  - можно масштабировать `rental-query` отдельно под высокий read-трафик;
  - `pricing` можно независимо развивать и оптимизировать;
  - проще реализовать предсказуемую деградацию (например, `pricing` временно недоступен — degrade только часть функционала).

Минусы:
  - усложнение деплоя и инфраструктуры;
  - нужны контракты между сервисами и кэш-слой (Redis).

Выбор: вариант с разделением на `rental-api`, `pricing`, `rental-query` принят как базовый, так как он лучше отвечает требованиям по отказоустойчивости, масштабируемости и предсказуемой деградации
